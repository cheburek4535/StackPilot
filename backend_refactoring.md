# StackPilot Backend Refactoring Plan

**ВНИМАНИЕ ДЛЯ АГЕНТА:** Этот документ описывает критические архитектурные долги и проблемы безопасности/стабильности, найденные в ходе "жесткого" технического аудита бэкенда (Rust/Tauri) проекта StackPilot. Твоя задача — методично исправлять эти проблемы, не нарушая работоспособность существующего функционала. 

При рефакторинге **НЕ ЛОМАЙ** контракты Tauri-команд (frontend зависит от них), но изменяй внутреннюю реализацию так, чтобы она стала production-ready.

---

## 1. ProjectCreator: Устранение Race Conditions (Гонка данных)
**Где:** `src-tauri/src/modules/project_creator/commands.rs` -> `start_project_execution`
**Проблема:** Метод инициализирует генерацию проекта без проверки, запущена ли уже другая генерация. Строка `running_flag.store(true, Ordering::SeqCst)` просто перезаписывает флаг. Если клиент отправит два запроса, бэкенд запустит две параллельные таски `tokio::spawn`, которые будут писать файлы в одну директорию, что приведет к фатальному повреждению проекта.
**План действий:**
1. Заменить `Arc<AtomicBool>` для `execution_running` на `Arc<tokio::sync::Mutex<bool>>` ИЛИ использовать `AtomicBool::compare_exchange`. 
2. Если генерация уже запущена, команда ДОЛЖНА немедленно возвращать ошибку (`Err("Generation is already in progress".to_string())`).
3. Защитить очистку `events_store` — она должна происходить только если мы эксклюзивно захватили право на запуск.

## 2. ProjectCreator: Реализация отмены задач (Cancellation)
**Где:** 
- `src-tauri/src/modules/project_creator/commands.rs` 
- `src-tauri/src/modules/project_creator/engine/mod.rs` (и цикл выполнения)
**Проблема:** Запущенный процесс генерации (внутри `tokio::spawn`) невозможно прервать. Если пользователь закрывает вкладку или хочет отменить создание (например, при зависшем `npm install`), процесс висит в фоне.
**План действий:**
1. Добавить `CancellationToken` (из `tokio_util::sync`) или кастомный `Arc<AtomicBool>` (как в Toolchain `JobEngine`) в структуру `ProjectCreatorState`.
2. Создать новую Tauri команду `cancel_project_execution`, которая будет активировать токен отмены и принудительно убивать дочерние процессы через `crate::core::process_registry::terminate_group("project_creator")`.
3. В `engine.execute(...)` перед запуском каждого `Step` проверять токен отмены. Если он активирован — немедленно прерывать пайплайн (возвращать статус `Aborted`).

## 3. ProjectCreator: Расщепление God Object (engine/mod.rs)
**Где:** `src-tauri/src/modules/project_creator/engine/mod.rs` (и метод `compose_recipe`)
**Проблема:** Файл содержит 17 000+ строк. Функция `compose_recipe` жестко кодирует (hardcode) графы файлов, пакеты и команды для *абсолютно всех* поддерживаемых фреймворков и инструментов. Это делает добавление новых фреймворков мучительным и нарушает Open/Closed Principle.
**План действий (Постепенный рефакторинг):**
1. Ввести систему "Провайдеров" (Framework Planners / Recipe Builders). Создать типаж (trait) `RecipeProvider`, который генерирует шаги для конкретного фреймворка (например, `NextjsProvider`, `RustProvider`).
2. Разбить `compose_recipe` на диспетчеризацию по этим провайдерам.
3. В идеале — вынести конфигурации шагов в декларативные YAML/JSON манифесты (или изолированные Rust-модули по директориям, e.g., `providers/frontend/react.rs`), чтобы ядро движка не знало о том, как собирается конкретный стек.

## 4. Изоляция Side-Effects
**Где:** `src-tauri/src/modules/project_creator/generators/mod.rs` (например, `FsCleanupGenerator`)
**Проблема:** В генераторах жестко зашита бизнес-логика третьих инструментов (например, удаление `.agents`, `.claude` директорий от Prisma).
**План действий:**
1. Сделать очистку Data-Driven. `FsCleanupGenerator` должен принимать список паттернов для удаления из `Step::Generate` конфигурации, а не хардкодить их внутри Rust-кода.
2. Провести ревизию других `Generator` реализаций на предмет подобных хардкодов и вынести параметры в конфигурацию (в `wizard_tree` или определения шагов).

## 5. Унификация Process Management
**Где:** По всему приложению.
**Проблема:** Сейчас логика работы с процессами размазана. `ProjectCreator` использует свой `ProcessRunner` (в `engine/process.rs`), `Toolchain` использует свои механизмы, а `DevLauncher` имеет мощный `workspace::process_manager`.
**План действий:**
1. Изучить возможность использования единого трейта `ProcessManager` (из `devlauncher/orchestrator.rs`) для управления всеми фоновыми процессами.
2. Убедиться, что при "жестком" завершении приложения (SIGTERM) все дочерние деревья процессов убиваются корректно на всех платформах (Windows, macOS, Linux).
